# CommerceAgent 终态回复与失败恢复升级方案

> 版本：v1.0  
> 日期：2026-09-16  
> 状态：`planned`  
> 范围：Run 终态回复、决策拒绝恢复、异常兜底、人工接管、前端终态展示与回归验证  
> 关联方案：[演示工作台透明化升级方案](./demo-workbench-transparency-upgrade-plan.md)

## 1. 目标与非目标

### 1.1 目标

本方案解决“流程执行失败但用户没有得到明确回复”的问题。无论 Agent 最终成功、需要补充信息、需要人工审核、被取消、超时还是失败，都必须在原会话中发布一条用户可见的最终状态消息，并在右侧执行面板显示对应的终态原因和可执行动作。

必须满足以下不变量：

1. 每个已受理的 Run 最多发布一条终态助手回复；
2. `completed`、`waiting_user`、`waiting_confirmation`、`waiting_human`、`failed`、`cancelled`、`expired` 都必须有明确的用户可见说明；
3. 工具成功不等于流程成功，只有完成最终回复并持久化成功后，Run 才能标记为 `completed`；
4. 决策校验失败不能静默结束，必须记录可诊断原因，并进入受控重试、人工接管或明确失败回复；
5. 失败回复不得声称业务操作已完成，也不得暴露 Prompt、密钥、隐藏思维链或内部堆栈；
6. 前端不能因为 HTTP 请求结束就允许继续提交，必须等服务端 Run 进入允许新消息的状态；
7. 所有测试必须是有明确超时和结束条件的短时测试，不设置连续 24 小时运行的测试。

### 1.2 非目标

- 本阶段不引入第三方 Agent 编排框架；
- 不把完整模型原文、隐藏推理或敏感工具参数写入前端日志；
- 不通过无限重试掩盖模型、工具或数据库故障；
- 不自动新建会话或自动重复发送用户消息来规避 Run 冲突。

## 2. 已确认的问题

当前失败 Run `aeb72fd4-7faa-4c27-ac82-e465bb5c2589` 的执行链为：

1. 意图分类成功，路由为 `order_query`；
2. `get_order_status` 调用成功，查到订单状态、物流单号和预计送达时间；
3. 模型再次提出 `get_delivery_tracking` 决策；
4. 该决策在工具执行前被 `DecisionValidator` 拒绝；
5. Run 进入 `failed(reason=decision_rejected)`，但没有追加 `assistant_response`。

因此当前用户看到的“执行失败”存在两个缺陷：

- 业务失败和安全校验拒绝没有被转换成用户能理解的结果；
- `execute_message_run()` 的异常和失败分支没有统一调用“发布终态回复”的单一出口。

## 3. 目标状态模型

### 3.1 Run 状态和用户回复的对应关系

| Run 状态 | 用户看到的回复 | 前端可执行动作 |
|---|---|---|
| `completed` | 已完成，包含可信业务结果 | 新消息、重试（可选） |
| `waiting_user` | 明确列出缺少的字段和填写示例 | 补充信息 |
| `waiting_confirmation` | 明确需要确认的操作、对象和风险 | 确认、取消 |
| `waiting_human` | 明确已转人工及原因 | 等待审核、查看工单 |
| `failed` | 明确未完成、失败阶段、可否重试 | 重试、新消息 |
| `cancelled` | 明确已取消，说明是否产生副作用 | 新消息 |
| `expired` | 明确已超时失效 | 重新发起、新消息 |

`running_*`、`routing`、`created` 不是终态，但必须有当前活动摘要，例如“正在请求模型决定下一步”或“正在调用订单查询工具”。

### 3.2 统一终态回复服务

新增 `TerminalResponseService`（名称可按现有模块约定调整），作为所有执行路径的唯一出口，负责：

- 根据 `RunStatus`、`reason_code`、最后成功工具结果生成安全的用户文案；
- 判断同一 Run 是否已经发布过终态回复；
- 在事务中追加助手消息和 `assistant_response` 事件；
- 只有消息和终态事件持久化成功后，才允许写入最终 Run 状态；
- 对重复调用保持幂等，避免重试或进程恢复造成两条终态回复。

建议接口：

```python
publish_terminal_response(
    *,
    context: RunContext,
    status: RunStatus,
    reason_code: str | None = None,
    result_summary: dict[str, object] | None = None,
    retryable: bool = False,
) -> TerminalResponse
```

`TerminalResponse` 至少包含：`content`、`status_label`、`reason_code`、`retryable`、`published`。

## 4. 失败处理策略

### 4.1 决策校验失败

决策校验必须保留严格拒绝边界，不能为了让演示“成功”而放宽安全校验。

处理顺序：

1. 记录结构化 `decision_validation_failed` 事件，包含 `error_code`、工具名、当前 step 和允许工具集合；不记录完整 Prompt 或敏感参数；
2. 若是无副作用的终端回复决策，最多进行一次受控语义修复；
3. 若是工具决策参数错误，最多进行一次格式/参数修复，且仍需完整经过 `DecisionValidator`；
4. 修复仍失败时：
   - 若已有可信只读工具结果，优先使用可信结果生成安全兜底回复并标记 `completed`，前提是回复不需要未获得的事实；
   - 若无法生成完整答案，创建人工工单并进入 `waiting_human`；
   - 如果人工接管不可用，进入 `failed`，发布明确失败回复并提供 `retry`。

推荐的本次案例兜底文案：

> 订单 ORD-DEMO-001 已查询到：当前已发货，预计 2026-09-16 送达，物流单号为 TRK-DEMO-001。物流明细查询未完成，未影响订单本身；你可以稍后重试，或转人工继续查询。

不得在没有工具证据时编造订单状态、物流单号或时间。

### 4.2 模型不可用、工具失败、数据库失败

按故障类型映射为稳定的 `reason_code`：

| 内部原因 | 用户回复重点 | 状态 |
|---|---|---|
| `MODEL_GATEWAY_ERROR` | 模型服务暂时不可用，未完成处理 | `failed` |
| `TOOL_EXECUTION_FAILED` | 指定查询未完成，未声称业务已完成 | `failed` |
| `UPSTREAM_TIMEOUT` | 请求超时，建议重试 | `failed` 或 `expired` |
| `DECISION_REJECTED` | Agent 生成的下一步未通过安全检查，业务未继续执行 | `failed` 或 `waiting_human` |
| `CHECKPOINT_PERSISTENCE_FAILED` | 系统未能确认处理结果，请勿重复执行，建议人工核查 | `waiting_human` |
| `UNEXPECTED_EXECUTION_ERROR` | 处理异常，已停止自动执行 | `failed` 或 `waiting_human` |

内部错误详情只进入服务端结构化日志和脱敏 Trace，前端显示稳定错误码和人类可读说明。

### 4.3 等待用户和等待人工

- `waiting_user` 必须在进入等待态的同一流程中发布提问，不能只写 `missing_slots`；
- 问题必须列出字段名、已有字段和示例，例如“请补充退款商品编号和退款原因”；
- `waiting_human` 必须创建或复用幂等工单，并发布“已转人工”的助手消息；
- 人工审核批准或拒绝后，必须继续发布对应结果，不能只更新侧栏状态；
- 恢复流程再次失败时，仍走统一终态回复服务，不能留下无回复的半终态 Run。

## 5. 后端实施设计

### 5.1 统一状态收口

检查并收口以下路径：

- `src/orchestration/demo_run_executor.py` 的正常完成、缺槽位、模型异常、只读循环异常和未知异常分支；
- `src/agent/loop.py` 的 `decision_rejected`、`model_unavailable`、`tool_execution_failed`、超时和 token 耗尽分支；
- `src/orchestration/pipeline.py` 的 checkpoint 失败和状态转换失败分支；
- 人工审核批准、拒绝、超时和恢复执行分支；
- 应用重启后的历史 Run 恢复和补偿任务。

所有分支都必须满足：

```text
accepted Run
  -> execute or wait
  -> persist terminal/waiting state
  -> publish one user-visible response
  -> expose allowed actions
```

若“写入状态”和“发布回复”无法在一个数据库事务中完成，必须使用 outbox 或可重放补偿记录，禁止先返回成功再异步丢失回复。

### 5.2 错误码和事件

新增或统一以下事件：

- `decision_validation_failed`
- `recovery_attempt_started`
- `recovery_attempt_succeeded`
- `recovery_attempt_failed`
- `terminal_response_published`
- `terminal_response_publish_failed`

事件 payload 只包含：`reason_code`、`retryable`、`fallback_used`、`status`、`step_id`、`tool_name`、耗时和脱敏摘要。禁止保存原始 API Key、系统 Prompt、隐藏推理和未脱敏 PII。

### 5.3 幂等和并发

为终态回复增加数据库约束或等价幂等控制：

- 一个 `run_id` 至多一个 `terminal_response_published`；
- 同一个 `run_id` 的恢复操作使用幂等键；
- 已进入终态的 Run 不得再次执行工具；
- 前端重复点击、SSE 重连、进程恢复都只能读取已有终态回复；
- 原会话存在活动 Run 时，返回明确的冲突状态和已有 `run_id`，不自动创建新会话。

### 5.4 API 响应契约

Run 查询接口应返回：

```json
{
  "run_id": "...",
  "status": "failed",
  "status_label": "执行未完成",
  "status_description": "订单查询已部分完成，但下一步决策未通过安全检查",
  "terminal_reason": "DECISION_REJECTED",
  "retryable": true,
  "allowed_actions": ["retry", "new_message"],
  "response_message_id": "..."
}
```

当终态回复尚未成功持久化时，接口应明确返回 `terminal_response_pending`，前端显示“正在整理最终结果”，而不是显示成功或永久加载。

## 6. 前端实施设计

### 6.1 终态消息展示

中间消息区按 Run 绑定助手回复，不依赖本地 loading 状态补文案。每个 Run 显示：

- 结果标签：已完成、等待补充、等待人工、执行未完成、已取消、已超时；
- 用户可理解的结果说明；
- 失败阶段和稳定错误码；
- “重试”按钮（仅 `retryable=true`）；
- “转人工/查看工单”按钮（服务端允许时）。

失败卡片必须明确写出：处理是否产生副作用、哪些步骤已成功、哪些步骤未完成。例如只读查询失败时，不能让用户误以为退款已执行。

### 6.2 发送锁定和恢复

- 发送后立即锁定输入、发送按钮和预置场景按钮；
- 锁定持续到 Run 进入 `completed`、`waiting_user`、`waiting_confirmation`、`waiting_human`、`failed`、`cancelled` 或 `expired`；
- `waiting_user` 允许用户在同一会话提交补充信息；
- `waiting_human` 只允许查看人工处理窗口和等待结果，不允许再次提交同一业务请求；
- SSE 断开时显示连接状态，并通过 Run snapshot 和 timeline 恢复，不自动重复 POST；
- 刷新页面后读取服务器终态回复，不能重置为“加载中”。

### 6.3 透明化日志

右侧 Trace 至少展示：

1. 模型请求开始、结束和失败；
2. 模型决策摘要；
3. 决策校验成功或拒绝及稳定原因；
4. 工具请求、工具返回和结果摘要；
5. 恢复尝试；
6. 最终状态和最终回复发布结果。

将“模型已返回但决策被拒绝”和“工具调用失败”显示为不同日志类型，避免用户把安全拒绝误解为订单系统故障。

## 7. 分阶段执行顺序

### Phase A：终态回复基础设施

- 梳理所有 Run 状态转换和异常出口；
- 实现 `TerminalResponseService` 与稳定错误码映射；
- 为终态回复增加幂等约束和读取字段；
- 补齐成功、等待用户、等待人工、失败、取消、超时回复；
- 增加 `terminal_response_published` 事件；
- 保证旧 Run 可通过补偿任务生成缺失的终态回复。

完成标准：构造任意受理 Run 后，所有终态都能查询到 `response_message_id` 或明确的补偿中状态。

### Phase B：决策拒绝恢复

- 从 `DecisionValidationError` 提取稳定 `error_code`，禁止依赖异常字符串；
- 增加一次受控终端回复/工具参数修复；
- 使用已有可信只读结果生成安全兜底回复；
- 不能兜底时创建人工工单；
- 记录恢复事件并限制最多一次恢复尝试。

完成标准：本次 `ORD-DEMO-001` 场景即使第二次模型决策被拒绝，也能得到包含已查到信息的最终回复，或者进入人工窗口，不再停留在无回复失败。

### Phase C：前端终态与透明日志

- 展示失败原因、局部成功结果和可执行动作；
- 接入恢复事件和终态回复事件；
- 页面刷新、SSE 断线和重复点击回归；
- 失败后允许显式重试，但不自动重发。

完成标准：用户不查看容器日志，也能判断 Agent 做过什么、哪里停止、是否产生业务副作用以及下一步能做什么。

### Phase D：补偿、监控和发布

- 增加启动时的缺失终态回复扫描；
- 增加 outbox 未投递告警和 Run 长时间无事件告警；
- 统计 `decision_rejected`、无回复 Run、重复终态回复和人工接管率；
- 先在演示环境灰度，再切换默认路径。

完成标准：服务重启后没有新的“终态但无用户回复”记录，指标能够按 reason code 定位问题。

## 8. 测试和验收

所有测试均采用有限次数、有限步骤和显式超时。单个测试建议超时 5～30 秒，整组回归测试在有限分钟内结束；不设置连续 24 小时运行的测试。

### 8.1 单元测试

- 每个 `RunStatus` 都能生成非空且不误导的用户回复；
- 同一 Run 重复调用终态服务只产生一条助手消息；
- `DECISION_REJECTED`、模型不可用、工具失败、数据库失败分别映射到正确文案和 `retryable`；
- 有可信工具结果时兜底回复只引用结果中的字段；
- 无可信证据时不得生成订单状态、金额、物流号等业务事实；
- 恢复最多执行一次，恢复失败能转人工或失败回复；
- 系统字段、Prompt、密钥和隐藏推理不会出现在事件 payload。

### 8.2 集成测试

- 订单查询工具成功、第二次决策拒绝：产生最终回复并标记已部分完成；
- 订单查询工具失败：产生失败回复，不发布虚假的业务成功消息；
- 退款缺少字段：发布明确补充问题，提交补充信息后继续原 Run；
- 退款进入人工审核：侧栏显示工单，批准和拒绝都发布最终回复；
- 模型超时、数据库短暂不可用、checkpoint 重放：不产生重复终态回复；
- Run 进入终态后再次 POST：服务端拒绝重复执行并返回已有 Run 信息。

### 8.3 前端验收

- 成功、失败、等待用户、等待人工、取消和超时各有可见卡片；
- 失败时输入锁定逻辑和重试按钮状态正确；
- 刷新后仍能看到最终回复和完整 Trace；
- SSE 断线不会导致重复发送或重复助手消息；
- 用户仅通过页面即可看到当前状态、最后动作、停止原因和可执行操作。

### 8.4 演示验收脚本

1. 发送“查询 ORD-DEMO-001 物流”，验证工具成功后最终回复出现；
2. 注入第二次决策拒绝，验证显示“已查询到的结果 + 物流明细未完成”，或出现人工窗口；
3. 发送退款请求，验证缺少信息时 Agent 主动提问；
4. 提交补充信息，验证人工审核卡片出现；
5. 分别点击批准和不批准，验证两条路径均有最终助手回复；
6. 在执行中连续点击发送、刷新页面、断开再恢复 SSE，验证只有一个 Run 且最终只出现一条终态回复。

## 9. 交付检查清单

- [ ] 所有终态均有助手回复或可重放的终态回复 outbox；
- [ ] `decision_rejected` 有稳定错误码、Trace 事件和用户文案；
- [ ] 只读工具已有结果时可安全兜底；
- [ ] 不能安全兜底时自动创建人工工单；
- [ ] 前端失败态不再无限加载，也不自动换会话；
- [ ] 重试是显式操作且幂等；
- [ ] 状态、日志、用户回复三者在刷新后保持一致；
- [ ] 完成短时单元、集成和前端验收，不运行连续 24 小时测试；
- [ ] 记录未解决的上游模型兼容性问题和后续优化项。

## 10. 风险与取舍

严格校验和兜底回复之间必须保持边界：兜底只能使用已经由可信工具成功返回的事实，不能把模型猜测转成业务结果。对无法安全解释的异常转人工，会增加人工工单数量，但比让用户看到无回复、重复提交或误以为操作成功更可控。

终态回复服务应优先保证“用户一定知道结果”，再优化文案和自动恢复率。任何恢复机制都必须有次数上限、截止时间和幂等键，避免执行堵塞和隐式重试。
